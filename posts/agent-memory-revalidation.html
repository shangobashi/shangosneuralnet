Idempotency Does Not Keep Agent Memory Correct

Shango Bashi · 19 Oct, 2026 · 9 min read

An agent can remember the wrong thing perfectly. It can preserve the source, avoid duplicate writes, survive a restart, and retrieve the same bad record every morning. All the machinery works. The record should no longer be there.

This is one of the less glamorous problems in building persistent agent memory. A conversation produces candidate knowledge. Some candidates become useful context. Others are temporary observations, weak inferences, or statements whose meaning depends on circumstances that have already changed. Once those candidates are stored, improving the extraction rules only solves half the problem.

Recent work on CADb at IssaLabs has included revalidating stored derivations, filtering transient material, and keeping retrieval artifacts synchronized after derivation. The implementation snapshot supports those changes. It does not establish that every memory is correct, or that the live system has universal reliability. What interests me here is the general contract underneath that work: a successful earlier write cannot be permanent permission to participate in future reasoning.

Two different promises

Idempotency makes repeated execution safe under a defined contract. Given the same request, retrying should not create another unintended effect. That is valuable when a process crashes after writing a result but before reporting success. The Amazon Builders’ Library discussion of idempotent APIs explains this operational problem well.

Memory maintenance introduces another variable: the rules can change. A candidate accepted under yesterday’s validator may fail today’s. Deduplicating by source identifier does not answer whether the stored interpretation remains admissible.

Consider a synthetic example. A session contains “prefer explicit timezone settings” and “the queue contains seven tasks.” An early extractor stores both. Later, the policy distinguishes standing preferences from momentary observations. The new extractor rejects the queue statement, but a cache says that this session has already been processed. Nothing new is written. Nothing old is removed.

The rerun is stable, cheap, and wrong under the new policy. A record’s processing history and its current eligibility are separate facts. I want a maintenance contract that checks both.

Revalidate the stored interpretation

The useful boundary is between retained evidence and active context. A source can remain available for audit without every interpretation of it remaining eligible for retrieval. Removing a derived candidate from active memory need not erase the underlying conversation.

For a fixed candidate corpus C and validation policy p, define the active projection as A = validate(C, p). Repeating that projection should be stable. Changing p should cause the affected candidates to be reconsidered, including candidates written before the change.

This is narrower than regenerating all knowledge with a model. Existing candidates can first pass through deterministic validation. Re-derivation becomes a separate decision for records that need reinterpretation. That separation matters when model calls are slow, expensive, nondeterministic, or dependent on unavailable source material.

The following is an illustrative Python example, written for this article. It uses synthetic data and a deliberately simple rule. It is not a CADb source excerpt, and its generation manifest is an example design rather than a claim about CADb’s runtime.

def snapshot(rows, policy):
    # Complete candidate snapshot; unique IDs and trusted kind labels assumed.
    ordered = sorted(rows, key=lambda row: row['id'])
    accepted = [row for row in ordered
                if policy == 'v1' or row['kind'] == 'rule']
    payload = {'policy': policy, 'rows': ordered}
    generation = hashlib.sha256(json.dumps(
        payload, sort_keys=True, separators=(',', ':')
    ).encode()).hexdigest()
    return accepted, generation

Under v1, both example records survive. Under v2, only the standing rule survives. Sorting by stable identity makes input order irrelevant. Hashing the policy and full candidate snapshot distinguishes a policy migration from an ordinary retry. It also detects content changes that leave the document count unchanged.

The labels here are trusted inputs. A real classifier can label a temporary observation as a rule, and this function will accept the mistake. The hash certifies identity of the serialized inputs; it certifies neither truth nor good classification. Changes to validation semantics must also change the policy identifier. Otherwise the manifest tells a misleading story.

Removing a row is not enough

A retrieval system usually has more than one representation of the same material. There may be a candidate file, a database row, a full-text index, and a vector index. Updating one does not automatically establish consistency across the others.

SQLite makes this particularly easy to demonstrate. With an external-content FTS5 table, the application is responsible for keeping the search index consistent with the content table. The FTS5 documentation describes the resulting pitfalls and the rebuild operation. A normal table read and a search query can expose different state when maintenance is incomplete.

For a small corpus, one understandable approach is to rebuild the active projection and its index together. The companion example initializes a content table, an external-content FTS5 table, and a generation manifest. Publication then happens inside one SQLite transaction:

def install(db, rows, policy, fail=False):
    accepted, generation = snapshot(rows, policy)
    # Schema is initialized separately, outside the publication transaction.
    with db:
        db.execute('DELETE FROM active')
        db.executemany('INSERT INTO active VALUES (?, ?)',
                       [(row['id'], row['text']) for row in accepted])
        if fail:
            raise RuntimeError('simulated interruption')
        db.execute("INSERT INTO search(search) VALUES ('rebuild')")
        db.execute('DELETE FROM manifest')
        db.execute('INSERT INTO manifest VALUES (?)', (generation,))
    return generation

The transaction matters because readers should not observe a new content projection paired with the previous index. The injected exception exercises the rollback path: the previous content and generation remain in place. This example uses Python’s default SQLite connection behavior and an in-memory database; it does not demonstrate crash durability under every filesystem or connection configuration.

If the search index lives in a separate service, a SQLite transaction cannot cover it. A stronger design builds a new index generation, validates it, then switches the serving reference. Old generations remain available until the switch succeeds. That design has its own coordination and cleanup costs. The invariant remains useful: serving should identify which source and policy generation produced the searchable state.

Test what must disappear

Retrieval evaluations naturally concentrate on finding the right answer. Memory maintenance also needs tests for answers that should have stopped being available. A positive query can keep passing while obsolete material remains searchable beside it.

I ran the standalone companion example with six tests. They cover a stable retry, policy-driven removal of an old search hit, interruption before index rebuild, changed content with an unchanged row count, an empty active projection, and input-order independence. All six passed in this execution environment. Run it with python memory-revalidation.py; it requires Python 3.8 or later and SQLite with FTS5 enabled.

The policy-change test first proves that “queue” retrieves the synthetic observation. It installs the stricter policy, then checks that “queue” returns nothing while “timezone” still retrieves the retained rule. This is a more useful assertion than checking that a filter function returned one fewer item. It crosses the boundary that the agent actually consumes.

These results establish behavior for the example and those cases. They do not measure CADb retrieval quality, semantic accuracy, latency, concurrent writers, or performance on a large corpus. Keeping that scope explicit is part of making the result useful.

The cost of reconsideration

Full revalidation is simple to reason about but costs work proportional to the candidate corpus, before rebuilding search structures. At larger scale, policy versions and dependency tracking can narrow the affected set. The optimization is only safe when that dependency information is complete. An untracked rule change can leave exactly the stale candidates the migration was meant to remove.

I would start with a complete, inspectable rebuild when the corpus permits it. Incremental invalidation is justified by a measured bottleneck, not by discomfort with doing obvious work twice. Re-derivation should have explicit budgets and retry rules so that an empty result does not become an endless stream of model calls.

Rejection records introduce another trade-off. They help explain why a candidate disappeared, but can duplicate sensitive source text. An audit entry can often retain an identifier, policy version, and reason code instead. Audit data also needs access and retention rules; calling something a log does not make it harmless.

And a validation change can itself be wrong. Keep enough provenance to inspect the decision and, where appropriate, restore a previous generation. Removing information from active retrieval should be deliberate and reversible where the underlying retention policy allows it.

Memory needs a revision contract

The useful question is what happens when the system changes its mind about what deserves to persist. Can it reconsider old interpretations without duplicating them? Can it remove a candidate from every serving surface? Can it demonstrate that removal through the retrieval interface?

Those are ordinary data engineering questions with unusual consequences. An agent may use a retrieved record to plan its next action, so stale admissibility can propagate into behavior. Better extraction helps. Better ranking helps. Neither replaces the ability to revise the corpus already being served.

I want persistent memory that can explain its current state and change that state coherently. Remembering more becomes useful once the system can also establish what it has stopped treating as knowledge.
