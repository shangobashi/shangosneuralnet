Idempotency Does Not Keep Agent Memory Correct

Shango Bashi · 19 Oct, 2026 · 9 min read

A session has already been processed, so the memory pipeline skips it. Sensible enough. The expensive work is done, the result is stored, and running the job again will not create another copy.

Then you improve the validator.

The new version rejects something the old version accepted. Perhaps a temporary observation was mistaken for a standing instruction. Perhaps a summary made a stronger claim than its source justified. New records now pass through better rules. Existing records keep their old approval because the pipeline has no reason to visit them again.

You can run that job successfully every day and keep serving the same mistake.

Recent memory work in CADb, the agent infrastructure I’m developing through IssaLabs, has included revalidating stored derivations and rebuilding retrieval artifacts after derivation changes. The interesting part is the relationship between those operations. Changing what gets accepted today has consequences for what was accepted months ago, and those consequences have to reach the search interface.

I want to work through that problem without turning this into a tour of private infrastructure. A small SQLite example is enough to expose the mechanics.

The record that never gets reconsidered

Suppose a conversation produces two candidate memories: “prefer explicit timezone settings” and “the queue contains seven tasks.” Both are accurate descriptions of something said. Only the first is useful as a standing rule. The second describes a queue at a particular moment.

An early policy accepts both. Later, you tighten the policy to retain standing rules and exclude temporary observations. On the next run, the extractor checks the session identifier, finds an existing result, and skips it. The queue statement survives indefinitely.

There is nothing mysterious about the failure. The skip condition answers whether work has been done. The validator answers whether its output belongs in the active corpus. Treating those as the same decision lets old output bypass every subsequent improvement to validation.

Idempotency is still useful here. Retrying an operation should not create duplicate effects; the Amazon Builders’ Library article on idempotent APIs gives a good account of why that matters. But safe retries make a promise about repeated execution under a particular contract. They cannot tell you whether that contract should still accept a record.

Once validation changes, the stored result needs another decision. That decision does not necessarily require another model call.

Recheck the candidates before paying to derive them again

Keep the source material separate from the interpretations eligible for retrieval. A conversation can remain available for inspection even when a candidate derived from it is removed from active memory. That makes correction possible without pretending the original conversation never happened.

For a candidate corpus C and policy p, the active set is simply A = validate(C, p). A rerun with the same inputs should produce the same set. A new policy should reconsider the existing candidates as well as the new arrivals.

Here is an illustrative implementation using synthetic data. The companion code is written for this article, not taken from CADb:

def snapshot(rows, policy):
    # Complete candidate snapshot; unique IDs and trusted kind labels assumed.
    ordered = sorted(rows, key=lambda row: row['id'])
    accepted = [row for row in ordered
                if policy == 'v1' or row['kind'] == 'rule']
    payload = {'policy': policy, 'rows': ordered}
    generation = hashlib.sha256(json.dumps(
        payload, sort_keys=True, separators=(',', ':')
    ).encode()).hexdigest()
    return accepted, generation

Version v1 accepts both records. Version v2 keeps only records labelled rule. The function sorts by stable identifier, so shuffling the input does not change the result. It also hashes the complete candidate snapshot together with the policy version, giving us a way to identify which inputs produced a searchable set.

A document count would miss a text replacement. This hash catches it, even if the number of records stays unchanged. It will also change when a rejected candidate changes, because the input includes the whole corpus. That is conservative: it may trigger work the active set does not strictly need, but it keeps the example easy to inspect.

The policy version has to change when its meaning changes. And the rule label is trusted here; if a classifier assigns it incorrectly, this function will faithfully preserve the error. Hashes identify data. The judgement about what belongs in memory still lives in the validation rules and the evidence behind each candidate.

Revalidating stored candidates this way is cheaper than asking a model to reinterpret every source. Re-derivation can be reserved for cases where the existing interpretation is insufficient. It also needs a retry budget, or a window that produces no acceptable knowledge can become a recurring expense.

Follow the deletion all the way to search

Now remove the queue observation from the active records. If its old text is still in the search index, the agent can retrieve it anyway. The candidate filter may be correct while the system continues to serve what it rejected.

SQLite’s external-content FTS5 tables make this distinction concrete. The content lives in one table; the full-text index is maintained separately. As the FTS5 documentation explains, keeping them consistent is the application’s responsibility. Reading the content table and querying its search index can give different impressions of the database when that maintenance is incomplete.

For a small corpus, I would start by rebuilding the active set and its index together. The example creates an active table, an external-content search table, and a manifest table holding the generation identifier. After schema initialization, an update looks like this:

def install(db, rows, policy, fail=False):
    accepted, generation = snapshot(rows, policy)
    # Schema is initialized separately, outside the publication transaction.
    with db:
        db.execute('DELETE FROM active')
        db.executemany('INSERT INTO active VALUES (?, ?)',
                       [(row['id'], row['text']) for row in accepted])
        if fail:
            raise RuntimeError('simulated interruption')
        db.execute("INSERT INTO search(search) VALUES ('rebuild')")
        db.execute('DELETE FROM manifest')
        db.execute('INSERT INTO manifest VALUES (?)', (generation,))
    return generation

The transaction covers the replacement records, index rebuild, and manifest update. If an exception interrupts the update before completion, it rolls back instead of leaving the new content paired with the old search index. The deliberately placed fail flag lets the test interrupt the operation after the records change but before the index rebuilds.

This is manageable because everything sits in one database. With a separate vector service, that transaction ends at the database boundary. One approach is to build and check a new index generation before switching readers to it, keeping the previous generation available until the switch succeeds. Now there is coordination and cleanup work to do. The practical requirement is still quite concrete: a search result must come from the corpus and policy version the application believes it is serving.

Prove the old answer is gone

A retrieval test usually starts with a question and an expected answer. For this change, I also want an answer that used to be retrievable and must stop appearing.

The policy-change test first searches for “queue” and checks that the observation appears. It then installs v2, searches again, and expects no result. A second query checks that the timezone rule remains available. Checking only the filtered Python list would miss a stale index; these assertions use the interface the agent would actually consume.

The runnable companion has six tests covering that migration, repeated execution, interruption before the rebuild, changed text with an unchanged record count, an empty active set, and reordered input. All six pass. Run it with python memory-revalidation.py, using Python 3.8 or later and SQLite with FTS5 enabled.

The empty-set case matters. It is tempting to treat zero output as an extraction failure and preserve the previous state. Sometimes that is the right response. Sometimes a stricter policy has correctly rejected everything. Those cases need an explicit distinction, otherwise “preserve the last good result” becomes another way to retain bad knowledge forever.

What I would optimize later

A complete revalidation scans the corpus, then a full rebuild pays the indexing cost again. For a corpus small enough to tolerate it, that is an understandable price for a process whose behavior is easy to inspect. I would measure it before adding incremental invalidation.

Incremental updates require knowing which records depend on the rule that changed. Missing one dependency leaves old material behind, potentially without any obvious failure in the job output. A faster maintenance loop is useful only if its account of affected records is complete enough to trust.

I would also keep a modest rejection history: candidate identifier, policy version, and reason for removal. Copying all the rejected text into another log creates a second retention problem. Keep enough to investigate a decision without casually duplicating the source material.

Finally, a new validator can be wrong. Provenance and previous generations are useful when a stricter rule removes something it should have kept. Correction should work in both directions, within whatever retention rules apply to the underlying data.

This changes what I would ask of a memory system before giving it more responsibility. Show me a record that was useful yesterday, make it ineligible today, and demonstrate that the agent can no longer retrieve it. Then interrupt the update halfway through and show me what readers see. That tells me something a growing document count cannot.

Scope

The CADb context is grounded in inspected implementation changes, not a verification of the live runtime. The code and six tests above use synthetic data and an in-memory SQLite database with Python’s default connection behavior. They demonstrate the stated update and rollback cases, not semantic classification accuracy, concurrent writers, filesystem crash durability, or CADb’s production reliability. The linked AWS account and SQLite documentation supply the retry and indexing background.
